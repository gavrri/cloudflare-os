# Revenue Control Tower / My Sales Desk — local prototype

This is an incomplete, local-only synthetic-data prototype. The original proposed contract is in `types.d.ts`; the implementation is narrower. The Gadget sources in `gadget/` show candidates, contact histories, period caps and metric trends, and submit company, candidate, contact permission, event, contract and amount records to OS approval. The local-only Gatekeeper and D1 setup are documented in `../../packages/gatekeeper-gavrri-sales/README.md`.

For a fresh local-only database, run the four initialization commands in that Gatekeeper README, then run `sh plans/gavrri-revenue-slice/run-local-demo.sh` from the repository root. Open `http://localhost:8787`, create a disposable local user, add 営業デモ on the Gatekeepers page, and create 営業ノート（ローカルデモ） from Explore. In the Gadget's Connections, select 営業デモ and add it as `SALES`. The script builds a temporary local blueprint; it is not published. D1 state is under `.wrangler/state` and must contain synthetic data only. The first local demo account claims this database, so use an isolated fresh checkout/state for each demonstration.

No email or form submission is performed. The local Gatekeeper is opt-in and only allows one synthetic account and one demo D1 scope; it is not a production membership or authorization design. Actual data, remote resources and deployment are out of scope. Private drafts are not automatically shared.

Core records stable company IDs and explicit company aliases, separate candidate offer/motion and registry/contact states, append-only events and evidence, period caps, contracts and monetary entries. Refusal applies across linked company identities and offers; unknown receipt cannot be automatically retried. Idempotency keys and database constraints protect repeated operations. Money is currency-scoped; no conversion occurs. MRR uses paid effective dates and divides annual amounts by twelve. Revenue, payment and forecast remain separate; missing confirmation is not zero. Coverage remains unverified even when confirmed records exist.

The Gadget supports updating a candidate's next action and explicit company linking through approval. Company-name changes, other candidate edits and writing period limits are not in the approved API and remain unimplemented. Migration preview is limited to an embedded synthetic example and never writes. Existing Gadget instances are snapshots; create a new local Gadget to pick up new source. Browser acceptance for the latest screen and mobile layout remains outstanding; the separate real OS RPC test covers approval, readback and Observer denial with synthetic data. The earlier standalone local prototype remains separate and is not a live source for this OS prototype.

Before any publication or real-data use, separately review and authorize a production membership and access model, Observer revocation, remote resources and migrations, backups, deployment and operational cost. None of those actions is performed by this local prototype.

The local dashboard source plots up to six months of confirmed revenue and payments, monthly MRR, paid company and contract counts, and new contracts and cancellations. Each series shows its values and units; missing values remain unconfirmed rather than zero. MRR and active counts use each month's final day, capped at the selected as-of date. The current backend does not establish complete coverage, so an absent new or cancelled contract remains unconfirmed. Offer, dataset and currency filters apply to each monthly query. The charts have not yet been applied to the existing workspace instance or verified in its browser.
