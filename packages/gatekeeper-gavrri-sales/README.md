# Sales Gatekeeper — local synthetic demonstration only

This is an opt-in local Worker and is deliberately **not** deployable: it has `wrangler.local.jsonc`, not `wrangler.jsonc`; normal release discovery ignores it. `node scripts/run-local.ts --local-sales-demo` explicitly includes it in the local multi-Worker simulation. Never use this config, fixed database ID or the synthetic account with real sales data. It is not a production authorization design.

Prepare a fresh **local** D1 database from the repository root (do not repeat these on an existing database):

```
pnpm exec wrangler d1 execute gavrri-sales-local-demo -c packages/gatekeeper-gavrri-sales/wrangler.local.jsonc --local --persist-to .wrangler/state --file packages/gavrri-sales-core/migrations/0001.sql
pnpm exec wrangler d1 execute gavrri-sales-local-demo -c packages/gatekeeper-gavrri-sales/wrangler.local.jsonc --local --persist-to .wrangler/state --file packages/gavrri-sales-core/migrations/0002_company_alias_version.sql
pnpm exec wrangler d1 execute gavrri-sales-local-demo -c packages/gatekeeper-gavrri-sales/wrangler.local.jsonc --local --persist-to .wrangler/state --file packages/gatekeeper-gavrri-sales/local-owner.sql
pnpm exec wrangler d1 execute gavrri-sales-local-demo -c packages/gatekeeper-gavrri-sales/wrangler.local.jsonc --local --persist-to .wrangler/state --file packages/gatekeeper-gavrri-sales/demo-metrics.sql
node scripts/run-local.ts --local-sales-demo
```

All data in these SQL files is fabricated. An existing demo database initialized with 0001 needs only the 0002 command once; back up the local `.wrangler/state` directory first and do not re-run the initial seed. The migration preserves existing records. The first explicitly provisioned local demo account claims the single owner row; a second account cannot claim it. Its same-vendor verifier checks account identity and database ownership when a collaborator opens a Gadget. No identity or scope is supplied by Gadget code. `getGatekeeperClassFor('sales://local-demo')` is restricted to the owner. The `SALES` binding exposes candidate reads, event reads, demo metrics, and proposals. Observation goes through the OS approval queue. Proposals are queued through the OS approval queue; only the OS invoking `applyAction` can write. A rejected action remains rejected. Identical request IDs return the original proposal status; differing payloads with the same ID fail. Concurrent calls on one Gatekeeper facet are serialized.

The local demo binds a whole D1 instance to one `demo` scope; it refuses actual metrics and financial proposals. Company, candidate, permission, event, contract, amount, next action and explicit company linking proposals require approval. The migration preview accepts no user file or text: it only inspects an embedded synthetic registry sample. It does **not** implement production membership, real grant provisioning, multi-tenant isolation, source import, or email/form sending. The isolated OS RPC test is `test/os-rpc-integration.mjs`; it requires a fresh disposable D1 and a separately started loopback OS. Never point it at an existing workspace or account.

Additional local-only RPCs expose companies, campaign limits and confirmed metrics for a requested month. Company, candidate, contact-permission, contract and amount changes are proposals; the OS approval queue must apply them before they are saved. Permission changes require evidence and the candidate version. Core's refusal and prior-contact guards still apply. Financial proposals accept only the demo dataset. `previewDemoRegistry()` reads a hard-coded synthetic CSV and never imports it. Pending proposals reuse request IDs only for identical payloads. These additions require real OS authorization and approval integration tests before any deployment decision.

The approved next-action and explicit alias proposals use optimistic versions and the OS approval queue. Alias approval shows both names and IDs, and explains that refusals apply across all offers after the link. Company renaming, candidate identity editing and period-limit writes are not exposed by this approved API.

`demo-list-extra.sql` is an optional, repeat-safe set of fabricated local examples, applied only after both Core migrations and `local-owner.sql`. It includes distinct submitted, form-accepted, automatic-reply, human-reply, unknown, refusal and skipped histories. These records are demonstrations, not imported CRM data. Candidate and event reads return at most 100 records per page with session-bound cursors. The upper rowid captured on the first page excludes later appends, which appear on refresh; fields can still change while paging. Cursors cannot be reused in a different session, account, result type, or candidate. Authorization and Observer checks run on every page. `companyRefused` means a refusal is recorded for the canonical company, including explicit aliases; false means only that none is recorded, not that outreach is permitted. Pending approval status is not exposed in the list.

The optional `test/paging-os-check.mjs` exercises 202 synthetic candidates and 101 events through an isolated OS, Gatekeeper and D1 and renders the Gadget in JSDOM. It requires a fresh disposable checkout and database on `127.0.0.1:8789`, the migrations and `local-owner.sql`, followed by SQL generated by `node test/generate-paging-fixture.mjs`. Run with `SALES_DISPOSABLE_DB=confirmed node packages/gatekeeper-gavrri-sales/test/paging-os-check.mjs`. It creates a disposable local test identity; never run it against the user demo or an existing database.
